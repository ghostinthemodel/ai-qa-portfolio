Strategy

Testing Personalised &
Non-Deterministic Systems

When outputs vary by design, traditional pass/fail testing breaks down. Here's my framework for maintaining quality confidence anyway.

⚡ The Core Challenges

  • Same input, different outputs on every run — traditional assertions fail
  • User-specific context means tests can't be replayed identically
  • Quality is subjective and context-dependent, not binary
  • Personalisation creates an explosion of test permutations
  • Model updates shift the output distribution for all users simultaneously
  • A/B experiments run concurrently, contaminating test signals
  • "Correct" is defined by user preference, not a ground truth

🎯 My Testing Approach

  • Test the distribution, not the instance — use statistical acceptance bands
  • Synthetic user persona library with seeded, reproducible profiles
  • Seed-controlled runs for local regression testing
  • Property-based testing: invariants that must hold regardless of output
  • LLM-as-judge evaluators for qualitative dimensions
  • Shadow mode deployment: compare new model vs prod silently
  • Cohort-based testing to isolate personalisation variables

Key Strategies — In Detail

1. Distribution Testing with Statistical Confidence Bands

Instead of asserting exact output equality, I run N iterations and assert the output metric (relevance score, sentiment, length, topic) falls within a pre-established distribution. I use Kolmogorov-Smirnov tests to compare run distributions against a known-good baseline, flagging regressions when the distribution shifts beyond a threshold — not when a single output looks "wrong".

2. Property-Based / Invariant Testing

Define properties that must be true regardless of output: "response always contains a recommended product when category is provided", "response never surfaces competitor brands", "personalised greeting uses the user's stored first name". These structural invariants hold even when the creative content varies, giving deterministic test signals in a non-deterministic system.

# Example: Invariant test for personalised recommendation engine def test_recommendation_invariants(user_profile, response): # These must hold regardless of which products are recommended assert response.product_count >= 1, "Must return at least 1 recommendation" assert response.product_count <= 5, "Must not overwhelm user" assert all(p.category == user_profile.preferred_category for p in response.products), "Must respect category preference" assert response.greeting.contains(user_profile.first_name), "Personalised greeting required" assert not any(p in COMPETITOR_LIST for p in response.brand_mentions)

3. Synthetic Persona Library for Reproducible Personalisation Tests

I build a library of 20–50 synthetic user personas with fully-specified, seeded preference profiles. Because the personas are fixed, tests are deterministic even when the model is not — I can track how recommendations for "Persona 07 (high-income, tech-forward, Melbourne)" change across model versions, isolating model regression from data drift.

4. Shadow Mode Canary Testing

Before any model or personalisation algorithm change goes live, route a percentage of real traffic to the new system in shadow mode — it processes requests but responses are logged, not served. I run automated quality metrics over the shadow logs and compare distribution vs production before promoting. This catches regressions in real-world personalisation context without any user impact.

5. LLM-as-Judge for Qualitative Dimensions

Use a secondary LLM (with a carefully designed evaluation prompt and rubric) to score outputs on dimensions that can't be reduced to a formula: helpfulness, tone appropriateness, personalisation relevance, response naturalness. I track these scores over time using control charts — flagging points that fall outside 3-sigma control limits as quality incidents, regardless of absolute score level.

Principles

My QA Philosophy
for AI Systems

"AI systems need quality frameworks that reflect their probabilistic nature — not retrofitted deterministic QA."

Traditional QA was built for deterministic systems. AI changes the rules. I believe quality in AI is about confidence intervals, not binary outcomes — and that the QA function needs to be a strategic partner in model development, not a downstream gatekeeper.

My approach combines rigorous data-driven evaluation with deep empathy for the end user experience — because a model that passes all your evals but frustrates users isn't a quality system.

  • 01
    Shift Evals Left Evaluation frameworks should be designed before the model is built, alongside the product spec — not after deployment.
  • 02
    Test Distributions, Not Instances One "bad" output is noise. A shifting distribution is a signal. Build statistical quality monitoring, not one-off assertions.
  • 03
    Safety is Non-Negotiable — Usability Matters Too Over-refusal is a quality failure. A model that refuses 30% of legitimate requests has a usability bug, not a safety win.
  • 04
    Automate the Measurable, Human-Review the Nuanced Automate schema, safety, and metric gates. Reserve human eval budget for the judgment calls no automated metric can make.
  • 05
    Evals Are Products Eval sets go stale. Rubrics drift. Treat your evaluation infrastructure with the same engineering rigour as your production code.
